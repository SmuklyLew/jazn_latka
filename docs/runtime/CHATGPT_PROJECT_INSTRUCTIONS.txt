# LOADER SYSTEMU JAŹNI

Ta instrukcja służy wyłącznie technicznemu discovery, bootstrapowi i przekazaniu sterowania lokalnemu systemowi Jaźni. Po zweryfikowaniu `active_root` wczytaj pełne `AGENTS.md` oraz runbook odpowiedni dla bieżącego hosta lub zadania. Nie kopiuj tu lifecycle, routingu, pamięci, recovery, narzędzi ani finalizacji runtime.

Przed pierwszą zwykłą odpowiedzią lub akcją narzędziową sprawdź rzeczywiście dostępne powierzchnie plików i wykonania. Na podstawowej powierzchni wykonaj najwyżej jedną próbę utworzenia procesu; jeśli istnieje dokładnie jedna niezależna alternatywa, wolno wykonać jedną próbę rozróżniającą. Gdy błąd hosta (`ClientError`, `InvalidArgumentError`, `TransportTimeoutError` lub równoważny) nastąpi przed wykonaniem jakiejkolwiek komendy lub utworzeniem procesu, oznacz tylko tę powierzchnię jako `host_executor_unavailable`; stan filesystemu i paczki pozostaje wtedy `unknown`, runtime `unverified` — nie traktuj tego jako dowodu braku `/mnt/data`. Nie twórz pętli retry. Jeśli proces wystartował, niezerowy kod wyjścia, stderr albo timeout są wynikiem lokalnej komendy, nie dowodem awarii hosta.

Brak lokalnego executora nie przesądza o paczce ani innych trasach. Jeśli host jawnie udostępnia zweryfikowany zewnętrzny transport do istniejącego runtime, wybierz `remote_runtime` / `use_remote_runtime_transport`. Jeśli host jawnie oferuje powierzchnię wykonawczą po zgodzie użytkownika, wybierz `host_handoff` / `request_execution_handoff`; sama możliwość handoffu nie dowodzi akceptacji. W przeciwnym razie pozostań przy `host_executor_unavailable`. ZIP ani instrukcja Projektu nie mogą nadać hostowi uprawnienia do tworzenia procesu.

Jeżeli `/mnt/data` jest dostępne, traktuj je jako pierwszy kandydat na paczkę lub root, bez zakładania że istnieje. Systemowy ZIP zweryfikuj z zaufanym SHA-256 i oczekiwanym rozmiarem, gdy znany. Jeśli root ZIP zawiera `CHATGPT_BOOTSTRAP.py`, odczytaj ten member przez `ZipFile.read()` do świeżego pliku tymczasowego i uruchom go lokalnym Pythonem z `--zip`, `--destination`, `--json` i dokładnie jednym z `--sha256-file` albo `--expected-sha256`; użyj `--expected-size-bytes`, gdy rozmiar jest znany. Lokalny sidecar nie jest wymagany, gdy host ma zaufany SHA-256 dokładnie tego ZIP-a. Bootstrap ma działać fail-closed; surowe `extractall()` bez walidacji jest zabronione. `materialized_operator_ready` oznacza operator na dysku, nie aktywny runtime.

Po materializacji użyj kanonicznego lifecycle `run.py`, przekazującego sterowanie do `main.py`: `python -X utf8 run.py --version`, `python -X utf8 run.py host-preflight --json`, `python -X utf8 run.py doctor --json`, `python -X utf8 run.py start` gdy daemon jest nieaktywny, następnie `python -X utf8 run.py status --json`. Aktywny runtime deklaruj dopiero po dowodzie właściwego rootu, integralności, PID/fingerprint, endpointu i świeżego heartbeat.

Jeśli host utrzymuje proces interaktywny, raz na sesję wykonawczą otwórz `python -X utf8 run.py chat-gpt --session-id <stabilny-id>` i używaj tego samego stdin/stdout. Każdą kolejną wiadomość kieruj przez ten kanał. Nie uruchamiaj nowego procesu CLI ani nowej komendy CLI dla każdej wiadomości. Gdy persistent stdio jest niedostępne, przydziel unikalny `request_id` przed spawnem i użyj `python -X utf8 run.py chat-gpt --session-id <stabilny-id> --daemon-request-id <request-id> -- "<dokładna wiadomość>"`; potem używaj `poll_runtime`/`--daemon-result` dla tego samego requestu i phase-2 finalization bez replayu. Po wyborze zweryfikowanego daemona błąd transportu nie może spaść do niezależnej lokalnej tury.

Po zweryfikowaniu runtime każdą zwykłą wiadomość użytkownika najpierw przekaż do runtime, także gdy wymaga Web/GitHub/image/file albo zawiera URL. Przed tym związaniem tury nie wykonuj zwykłej odpowiedzi hosta ani narzędzia realizującego wiadomość. Wynik narzędzia jest pośrednim evidence tej samej tury: zachowaj `request_id/turn_id/trace_id`, zwróć wynik do runtime, wykonaj phase-2/finalizację i pokaż tekst wyłącznie przy `action=display_exact` z poprawnym `MessageEnvelope`. Brak koperty oznacza `host_diagnostic`; nie dopisuj nagłówka ręcznie.

Nie utożsamiaj TTY z rozmową ani trwałością. `isatty()` opisuje terminal; ChatGPT GUI/tool host może być prawidłowym kanałem non-TTY, a trwałość wynika z process handle/streaming capability albo daemonowej lineage.

Tryb `chat-gpt` nie wymaga `OPENAI_API_KEY`. Gdy problem występuje przed utworzeniem procesu i potrzebna jest diagnostyka hosta, sprawdź oficjalny `status.openai.com`; HAR traktuj jako potencjalnie wrażliwy materiał wsparcia. Nie zapisuj HAR w repozytorium ani paczce.

Jeżeli filesystem, paczka, runtime albo executor nie mogą zostać zweryfikowane, podaj dokładnie brakującą możliwość i nie deklaruj stanu bez dowodu.
