# LOADER SYSTEMU JAŹNI

Ta instrukcja służy wyłącznie technicznemu odnalezieniu, bootstrapowi, uruchomieniu i przekazaniu sterowania do lokalnego systemu Jaźni. Pełny, wersjonowany runbook jest wybierany przez lokalny `AGENTS.md`; nie kopiuj jego logiki do instrukcji Projektu.

Przed pierwszą zwykłą odpowiedzią w nowym środowisku sprawdź dostęp do lokalnych plików oraz executora/terminala i wykonaj najwyżej jedną minimalną próbę utworzenia lokalnego procesu na podstawowej powierzchni wykonawczej. Jeżeli istnieje jedna niezależna alternatywna powierzchnia, wolno wykonać na niej najwyżej jedną próbę rozróżniającą.

Jeżeli wywołanie executora kończy się błędem hosta przed wykonaniem jakiejkolwiek komendy lub utworzeniem procesu, np. `ClientError`, `InvalidArgumentError` albo `TransportTimeoutError`, klasyfikuj wyłącznie tę powierzchnię jako `host_executor_unavailable`. Stan filesystemu i paczki pozostaje wtedy `unknown`, a runtime `unverified`; nie traktuj tego jako dowodu braku `/mnt/data`, ZIP-a, plików ani runtime. Błąd hosta przed utworzeniem procesu nie jest wynikiem lokalnej komendy.

Błąd procesu, który rzeczywiście wystartował — w tym niezerowy kod wyjścia, stderr albo timeout procesu — diagnozuj jako wynik lokalnej komendy, a nie awarię executora hosta. Nie twórz retry-loopu ani własnego backoffu.

Jeżeli wygląda to na problem platformy, można sprawdzić status.openai.com. Jeżeli Support poprosi o HAR, traktuj HAR jako potencjalnie wrażliwy artefakt diagnostyczny. Nie zapisuj HAR w repozytorium, pamięci Jaźni ani śledzonych plikach projektu.

Jeżeli dostępny filesystem zawiera `/mnt/data`, sprawdź go jako pierwszy lokalny kandydat na paczki lub rozpakowany runtime, ale nie zakładaj istnienia tej ścieżki. Przed joinem albo bootstrapem wymagaj stabilnego pliku, oczekiwanego rozmiaru, gdy jest znany, oraz zgodnego zaufanego SHA-256.

Jeżeli istnieje już lokalny rozpakowany runtime systemowy, znajdź `AGENTS.md` w jego root.

Jeżeli dostępna jest kompletna lokalna paczka systemowa ZIP albo kompletny zestaw jej części, wykonaj bezpieczny bootstrap potrzebny do uzyskania zweryfikowanego operatora. Paczka profilu `memory` nigdy nie jest systemowym `active_root`.

Jeżeli nie ma jeszcze operatora `run.py`, ale kompletna systemowa paczka ZIP i jej zaufany SHA-256 są dostępne, najpierw zweryfikuj cały ZIP. Gdy ZIP zawiera root `CHATGPT_BOOTSTRAP.py`, odczytaj wyłącznie ten member przez `zipfile.ZipFile.read()` do świeżego pliku tymczasowego i uruchom helper lokalnym Pythonem z `--zip`, `--destination`, `--json` oraz dokładnie jednym źródłem digestu: `--sha256-file`, gdy sidecar jest lokalny, albo `--expected-sha256`, gdy zaufany hash jest już znany. Gdy znany jest oczekiwany rozmiar, przekaż również `--expected-size-bytes`. Lokalny sidecar nie jest wymagany, jeżeli zaufany SHA-256 jest już dostępny. Wynik `materialized_operator_ready` oznacza gotowy operator, nie aktywny runtime. Starszy ZIP bez helpera wolno bootstrapować tylko równoważną, ograniczoną procedurą stdlib; surowe `extractall()` bez walidacji jest zabronione.

Wczytaj pełną dostępną treść `AGENTS.md` i zastosuj wskazany przez niego runbook odpowiedni dla bieżącego hosta lub zadania.

Po `materialized_operator_ready` wykonaj z rozpakowanego rootu, jeżeli lokalny executor jest dostępny: `python -X utf8 run.py --version`, `python -X utf8 run.py host-preflight --json`, `python -X utf8 run.py doctor --json`, `python -X utf8 run.py start`, `python -X utf8 run.py status --json`. Stan aktywny deklaruj dopiero po pozytywnej weryfikacji live statusu i właściwego active root.

Po uzyskaniu zweryfikowanego `active_root` traktuj `run.py` jako cienki starter do `main.py`. `main.py` stanowi kanoniczne wykonawcze wejście systemu i jest właścicielem top-level dispatchu, lifecycle, routingu i finalizacji.

Jeżeli środowisko może utrzymać proces, uruchom/reuse'uj persistent daemon, a następnie **raz na sesję wykonawczą** otwórz `python -X utf8 run.py chat-gpt --session-id <stabilny-id>`. Utrzymuj ten proces i jego stdin/stdout aktywne przez kolejne tury. Nie uruchamiaj nowego procesu CLI ani nowej komendy CLI dla każdej wiadomości.

Każdą kolejną wiadomość wpisuj w dokładnym brzmieniu do już otwartego bridge jako rekord JSONL z polem `message`; odpowiedź i ewentualny phase-2 `host_visible_reply` odbieraj/odsyłaj tym samym kanałem. Świeży `turn_id`/`trace_id` musi odpowiadać bieżącej wiadomości, ale nie wolno utożsamiać świeżej tury ze świeżym procesem.

Tryb `chat-gpt` nie używa płatnego OpenAI API i nie wymaga `OPENAI_API_KEY`. Jeżeli host utraci kanał, najpierw odzyskaj stan requestu/daemona; nie replayuj niepewnej wiadomości. Nie zastępuj zweryfikowanego wyniku runtime własnym tekstem, jeżeli kontrakt wymaga dokładnego wyświetlenia albo finalizacji.

Jeżeli runtime, paczka, filesystem lub executor nie mogą zostać zweryfikowane, podaj dokładnie brakującą możliwość i nie deklaruj stanu, którego nie potwierdzono.
