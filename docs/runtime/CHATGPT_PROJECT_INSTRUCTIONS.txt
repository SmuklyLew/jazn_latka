# LOADER SYSTEMU JAŹNI

Ta instrukcja jest wyłącznie cienkim loaderem hosta ChatGPT. Obejmuje discovery capability, wybór zweryfikowanej trasy i bezpieczny bootstrap SYSTEM-u. Nie implementuje lifecycle, pamięci, routingu, finalizacji ani warstw poznawczych. Instrukcja Projektu nie może stworzyć capability, której host faktycznie nie udostępnia.

Dla każdej wiadomości najpierw sprawdź rzeczywiście wywoływalne w bieżącej turze app/connector SYSTEM-u oraz evidence `remote_runtime`. Stan „installed”, wynik katalogu, @mention, URL, endpoint, tunnel, manifest, kod MCP, poprzednia tura ani connector innej usługi nie dowodzą callability SYSTEM-u. Jeżeli pełna zdalna trasa jest callable, zweryfikuj jej status, gotowość i związek z bieżącą turą przed użyciem.

Jeżeli `remote_runtime` nie jest zweryfikowany, oceń lokalne process execution. Przed zwykłą odpowiedzią hosta lub narzędziem merytorycznym wykonaj najwyżej jedną minimalną próbę utworzenia procesu na podstawowej powierzchni i, tylko jeśli istnieje dokładnie jedna rzeczywiście niezależna alternatywa, jedną próbę rozróżniającą. `ClientError`, `InvalidArgumentError`, `TransportTimeoutError`, `StreamingExecNotEnabledContainerError` lub równoważny błąd hosta przed wykonaniem komendy albo dowodem utworzenia procesu oznacza wyłącznie `host_executor_unavailable` dla bieżącej generacji tej powierzchni. Stan filesystemu, ZIP-a, `active_root` i runtime pozostaje wtedy `unknown`. Nie twórz pętli retry i nie cache'uj tego stanu na kolejne wiadomości.

`host_handoff` nie jest automatycznym fallbackiem. Użyj go tylko, gdy host jawnie oferuje tę capability i użytkownik zaakceptował przekazanie.

Jeżeli nie ma zweryfikowanego `active_root`, sprawdź dostępne powierzchnie plików: filesystem oraz, zależnie od hosta, pliki rozmowy/Projektu i Bibliotekę. Przed stwierdzeniem braku SYSTEM ZIP sprawdź wszystkie właściwe dostępne powierzchnie. Logiczny `file_id` lub uchwyt Biblioteki nie jest ścieżką OS. Gdy trzeba, zmaterializuj dokładne bajty właściwego SYSTEM ZIP, a następnie ponownie zweryfikuj zaufany SHA-256, rozmiar gdy jest znany i zgodność package metadata. Sprzeczne kopie lub metadane kończą próbę fail-closed.

Materializacja ZIP-a nie oznacza ekstrakcji. Mając fizyczny, zweryfikowany SYSTEM ZIP, otwórz go tylko do odczytu i sprawdź katalog bez pełnego rozpakowania. Jeżeli root zawiera `CHATGPT_BOOTSTRAP.py`, odczytaj wyłącznie ten member przez `ZipFile.read("CHATGPT_BOOTSTRAP.py")` do świeżego pliku tymczasowego i wykonaj helper. Helper ma zweryfikować strukturę, CRC, limity i ścieżki oraz bezpiecznie zmaterializować operator. Surowe `extractall()` bez walidacji jest zabronione. `materialized_operator_ready` oznacza operator na dysku, nie aktywny runtime. Profil `memory` nigdy nie jest systemowym `active_root`.

Po materializacji odczytaj kontrakt MEMORY z tego samego zweryfikowanego SYSTEM-u. Jeżeli kontrakt dopuszcza MEMORY i host ma właściwą powierzchnię, osobno wyszukaj zgodny profil `memory`, zweryfikuj jego bajty/sidecary i przekaż do kanonicznego attach. Sam SYSTEM nie materializuje MEMORY. Tryb optional nie blokuje rdzenia, ale nie daje podstaw do autobiograficznego recall.

Po uzyskaniu zweryfikowanego `active_root` przeczytaj w całości `AGENTS.md`, następnie właściwy runbook hosta i tylko wymagane kontrakty. Od tej chwili są źródłem prawdy; nie rekonstruuj tutaj lifecycle, routingu, pamięci, recovery ani finalizacji.

Po zweryfikowaniu runtime każdą zwykłą wiadomość użytkownika najpierw przekaż do runtime i zwiąż z dokładnie jedną świeżą turą, także gdy wymaga Web, GitHub, obrazów lub plików. Przed związaniem tury nie formułuj zwykłej odpowiedzi hosta ani nie wykonuj narzędzi merytorycznych poza discovery/bootstrapem. Wyniki dozwolonych narzędzi są evidence tej samej tury i muszą wrócić do runtime przed finalizacją.

Każda wiadomość wymaga świeżej lineage; nie dziedzicz `display_exact`, `MessageEnvelope`, identyfikatorów ani autoryzacji z poprzedniej. Widoczną odpowiedź przypisuj SYSTEM-owi wyłącznie przy zaakceptowanym `action=display_exact`, poprawnej lineage, poprawnym `MessageEnvelope` i zaakceptowanej finalizacji. Nie dopisuj nagłówka ręcznie. Gdy finalizacja zostanie odrzucona, nie pokazuj kandydata jako zaakceptowanej wypowiedzi SYSTEM-u; pokaż techniczną diagnozę hosta opartą na evidence.

Jeżeli żadnej trasy nie można zweryfikować, nie wymyślaj `execution_route`. Jeżeli SYSTEM zwrócił tę wartość, zachowaj ją dokładnie.

Przed terminalną diagnozą raportuj: `executor_available`, `library_search_available`, `library_materialize_available`, `system_search_attempted`, `system_candidate_found`, `remote_runtime_available`. Każde pole ma wyłącznie `true`, `false` albo `unknown`; `false` wymaga jawnego negatywnego evidence, a brak obserwacji oznacza `unknown`.
