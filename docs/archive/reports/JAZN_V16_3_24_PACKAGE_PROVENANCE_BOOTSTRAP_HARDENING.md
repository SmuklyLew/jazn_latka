# Jaźń v16.3.24 — Package Provenance Bootstrap Hardening

## Scope

This patch repairs the fail-closed startup path for system packages generated by `jazn_pack_generator.py` v8.6 with Git/GitHub integration disabled, while preserving the stricter release-provenance boundary.

Release identity: `16.3.24-package-provenance-bootstrap-hardening`.

## Reproduced failure

A v16.3.23 `system` package produced by generator v8.6 with `git_integration_enabled=false` had valid archive SHA-256/CRC, a valid package sidecar, and a valid `PACKAGE_INTEGRITY_MANIFEST.json`, but bootstrap rejected its truthful `SOURCE_PROVENANCE.json` because the runtime required Git commit/tree identifiers even for `generation_mode=filesystem_snapshot`.

After the staging gate was repaired, the persistent daemon reproduced the same rejection in its independent provenance gate. Both consumers therefore needed to converge on the same verified offline-snapshot predicate.

## Truth boundary

`filesystem_snapshot` is accepted for runtime activation only when all required conditions are satisfied, including:

- runtime/system-smoke profile;
- version agreement with the subject runtime root;
- `SOURCE_PROVENANCE.json` protected by the package integrity manifest;
- explicit `source_commit_policy=not_applicable_git_integration_disabled`;
- `base_version == runtime_version`;
- no asserted Git/GitHub repository, remote, branch, commit, tree, tag, dirty state, commit date, or PR identity.

The patch does **not** fabricate Git identifiers. Offline snapshot verification can satisfy runtime activation prerequisites but cannot by itself make release metadata current or the package `release_ready`. Release, development, and export provenance profiles retain their stricter requirements.

## Generator v8.6 two-file contract

The generator remains a two-file tool:

1. `tools/jazn_pack_generator.py`
2. `tools/jazn_pack_generator_settings.json`

Historical helper modules are bundled inside the Python entrypoint and are not physical source files. The v8.6 static-analysis fix therefore:

- uses `_bundle_types.ModuleType` consistently;
- obtains bundled modules directly from `_load_bundled_module(...)`;
- removes static imports that pointed at intentionally deleted helper files;
- keeps `tools/jazn_pack_generator.py` under Pyright rather than weakening the CI contract.

A regression test locks the two-file bundle contract and verifies that the legacy helper files remain absent.

## CI contract repairs found during the defect loop

The defect loop also exposed stale validation contracts. They were corrected rather than bypassed:

- `release-hardening.yml` no longer passes a deleted helper file to Pyright;
- generator tests track `GENERATOR_VERSION == 8.6` and `SETTINGS_SCHEMA == jazn_pack_generator_settings/v8.6`;
- release-version tests track `16.3.24-package-provenance-bootstrap-hardening`;
- no Pyright rule, pytest selection, code-health budget, or security gate was weakened to obtain a pass.

## External engineering basis

The implementation follows the principle that provenance should make only claims the producer can actually substantiate. When Git integration is intentionally disabled, package content integrity is bound to cryptographic digests and the integrity manifest rather than invented Git history. Static-analysis compatibility likewise keeps dynamically bundled runtime modules behind the bundling loader instead of presenting nonexistent source modules to Pyright.
